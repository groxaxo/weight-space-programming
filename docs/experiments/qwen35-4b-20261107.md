# Qwen3.5-4B coding assistant: implementation, experiments and findings

Date: 7 November 2026, Pacific/Auckland. Execution host: `100.85.200.54` (`4790`).
Repository starting commit: `17611902e37ff76e7bf0d5e7b3012e8bd55fffbe`.

## Decision

**Keep the official base model as the default. No fine-tuned adapter passed the
complete acceptance gate.** The repository now has a reproducible training,
serving and evaluation workflow, with real OpenCode/Hermes integration evidence.
The experiments do not establish a perfect coding assistant or equivalence to a
frontier model. Failed trials and infrastructure corrections are retained.

The base solved 128/164 HumanEval tasks (78.05%), 6/8 authored Python tasks and
6/6 multi-turn tool scenarios. Both installed clients passed the initial
single-module file-edit fixture. The larger scheduler trial, recorded below,
sets a stricter practical limit on repository-level reliability.

Machine-readable measurements, identities, checkpoint hashes and changed cases
are in [the experiment record](qwen35-4b-20261107.json). Operational commands are
in [the coding workflow](../coding-assistant.md). Model/data terms are in
[the attribution record](../coder-attribution.md).

The original p50c work remains a reproduction of published sparse weight edits.

not demonstrate a new activation-based weight-programming algorithm or transfer
of a frontier assistant's complete capabilities into four billion parameters.

## Hardware, pinned inputs and runtime

The requested .54 machine has one NVIDIA RTX 3060 with 12 GB VRAM and 32 GB RAM.
The base is `Qwen/Qwen3.5-4B`, revision
`851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`. The authenticated model-input record covers 12
required files, approximately 9.34 GB. The original downloaded weights stay
unchanged. Training, model inference, native conversion and real-client trials
ran on .54. CPU source packaging was also performed on the controlling Mac.

The measured NF4 runtime used PyTorch 2.11.0, Transformers 5.22.1, PEFT 0.21.2,
bitsandbytes 0.49.2, flash-linear-attention/fla-core 0.6.0, NF4 double
quantization and BF16 compute. `causal-conv1d` was absent; the correct reference
convolution is substantially slower. The serving identity records these versions.

Generation was text-only, non-thinking and greedy, with a 1,024-token output
budget during development/HumanEval. Interactive sessions have a 16,384-token
total context window, including input and reserved output, with up to 2,048
output tokens and serialized requests. SSE
emits one completed delta rather than individual tokens. This is a bounded
single-user experiment endpoint, not a concurrent production model service.

## Corpus and training recipe

The input pool contains 512 coding examples from NVIDIA OpenCodeInstruct and 128
complete Nous Hermes function-calling conversations. The split is 576 training
and 64 validation conversations. The prepared files contain 140,065 supervised
training tokens and 16,409 supervised validation tokens, with maximum sequence
length 1,536. Task and exact prompt identities are disjoint across this split.

| Source | Pinned revision | Terms |
|---|---|---|
| NVIDIA OpenCodeInstruct | `8f3ba5bafe4d6e8db46082cf7ae6741bc370604d` | CC-BY-4.0 |
| Nous Hermes function calling v1 | `dae3e1d28cfbcf4b915c04ea1e072030529b4bda` | Apache-2.0 |
| Official Qwen3.5-4B | `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a` | Apache-2.0 |
| OpenAI HumanEval, evaluation only | `7dce6050a7d6d172f3cc5c32aa97f52fa1a2e544` | MIT |

OpenCodeInstruct rows were selected using the publisher's passing-test metadata;
that metadata is not an independent correctness proof. Tool conversations were
converted into the model's native chat format and rejected if calls, roles or
schemas were incomplete. Public source files were authenticated before use.
Private user conversations/repositories and evaluator reference solutions were
not imported as training targets. Exact split checks do not prove semantic
disjointness, nor exclude public benchmark material in pretraining or source data.

Both full runs used rank 16, alpha 32, seed 20261106, gradient accumulation 8,
one epoch and 72 optimizer steps. LoRA targeted 248 language-layer linear
matrices, comprising 32,464,896 parameters. The initial learning rate was 5e-5;
the second run changed only the rate to 5e-6. Saved steps 18, 36 and 54 were
screened where available. Step 18 represents 0.25 epoch. All 496 adapter factors
were checked for finite values and authenticated against completed-run records.

## Frozen acceptance requirements

The NF4 gate requires at least 7/8 coding cases, all six tool scenarios, a
development improvement, no per-case development regression, all 164 paired
HumanEval results with solved count at least the base's 128, both actual client
edit fixtures passing completed independent assertions, and finite improved
held-out loss. Base/candidate identities must match in revision, quantization,
runtime, protocol, evaluator, task identities and execution sandbox.

The separately declared [native contract](../native-acceptance.md) requires the
same development floors and no regressions, full paired HumanEval non-regression,
both real clients and improved finite held-out loss. It also requires a functional
development gain or a strictly higher HumanEval count. Different protocol hashes
cannot reuse one another's baselines. These thresholds were not lowered after
observing rejected runs. The supplementary project trial does not relax them.

The initial higher-rate run reduced validation loss to approximately 0.194329,
but showed a coding regression. Its clean step-18 development evaluation scored
6/8 coding and 6/6 tools, with regressions in escaped-field parsing and chunk-size
validation. Step-36/54 screens also failed the chunk-size requirement. Those
partial screens are rejection evidence, not complete benchmark runs.

Early diagnostic tool runs used an incomplete Qwen end-of-turn stopping rule.
The server was corrected to recognize token IDs 248044 and 248046. Those old
diagnostics were excluded from the accepted paired comparison. The final NF4
protocol hash is `95ccac67c7d4d58eaf644439cf4076e50bca2f580b9e3b89eed6ba5d9aaad82d`.

Lower validation loss measures fit to the chosen validation distribution. It did
not predict monotonic coding/tool improvement in these experiments. Replacing
the base with either fully benchmarked adapter would knowingly reduce the measured
broader solved count, so neither was promoted.

## Actual OpenCode and Hermes results

The initial fixture asked each installed CLI to read and repair `calc.py` through
file tools. Both left the fixture tests unchanged, edited only the permitted
module and passed independent Docker assertions. The lower-rate adapters also
passed both initial fixtures. These are real CLI workflows, not simulated
OpenAI-shaped tool responses.

| Base-profile client | Installed version | Complete fixture time | Independent result |
|---|---|---:|---|
| opencode | 1.18.32 | 47.8 s | Passed |
| hermes | Hermes Agent v0.22.2+2320.g27a92f6 (2026.9.24) · stable · local 27a92f6df064 | 97.9 s | Passed |

These times include startup and the complete fixture. The initial CLI/file-tool
processes are not a claim of host OS confinement; their final code is graded in
the independent sandbox. A provider working with a small edit does not qualify
larger projects, arbitrary terminal/MCP use or a user's existing client defaults.

The additional scheduler trial required two modules, generator-safe validation,
stable topological ordering, cycle/unknown-dependency rejection, unchanged tests
and actual terminal execution. OpenCode ran entirely inside its network-disabled
container, accessing the model through a temporary Unix socket relay. Its final
modules failed independent tests after a 1,000-second timeout; repeating checks
did not repair the implementation.

The first Hermes attempt exposed an infrastructure fault and was stopped. Its
managed worker selected the local terminal backend despite launch environment
variables requesting Docker. Actual tool events returned host repository paths,
and no labeled sandbox container was observed. No model write event was observed
before termination. This attempt is **unqualified infrastructure evidence**, not
a valid contained model-quality trial. Its original logs/report remain immutable.

The root cause was the session configuration boundary: this installed Hermes
version freezes worker configuration, while `--safe-mode` ignores the task
profile. A direct backend probe had worked but had not traversed the managed CLI.
The harness now creates a fresh explicit profile containing `terminal.backend:
docker`, a pinned image, one fixture mount, disabled networking, bounded resources
and empty MCP registration. It uses `--ignore-rules` without `--safe-mode` for
this configured project session. No global Hermes configuration or existing user
profile was modified.

A new synthetic-provider control traversed the actual installed Hermes CLI and
managed worker. Its terminal command confirmed UID 1000, `/workspace` fixture
visibility, loopback-only interfaces, no Docker socket and absence of the host
repository path. Docker inspection independently confirmed the trial's mounts,
network and resource limits. This control involved no Qwen inference and is not
a model score. The corrected real Hermes project trial is reported below.

| Latest scored project trial | Complete workflow | Independent final modules | Time |
|---|---|---|---:|
| opencode | Failed | Failed | 1000.0 s |
| hermes | Failed | Failed | 414.9 s |

The original test-command recognizer also missed the equivalent explicit form
`python3 -m unittest -v test_scheduler`. A failing regression control reproduced
the problem, then the allowlist was widened to the exact fixture module forms.
The equivalent trailing `2>&1` redirection is also accepted.
It still rejects prose, `echo`, unrelated modules and chained shell commands.
Auditing saved engine events correctly detects the test runs. No answers were
regenerated and no independent code result changed. No complete workflow decision changed. OpenCode's
timeout and failing final code independently determine its rejection.
Hermes also marks a completed nonzero test subprocess as a tool error. The
detector now counts that execution while still rejecting policy-blocked launches;
whether the code passes remains the independent grader's separate decision.

## CPU merge and native Q8 experiments

The CPU compiler performs FP32 `B @ A * alpha/r` one matrix at a time, rounds
to BF16 using round-to-nearest with ties to even, preserves original shard layout
and verifies every byte outside the edited spans. The real compile verified all
248 edited matrices and all remaining bytes of the copied checkpoint. That
establishes artifact integrity, not inference equivalence after rounding.

The existing protected llama.cpp converter initially could not reshape one
hybrid-head LoRA layout. A process-local patch now permutes B for row reordering
and A for column reordering. Golden controls compare the factorized update with
the corresponding dense permutation. The real exports contain 496 finite FP32
factors, with 96 row and 24 column permutations. Protected converter files were
hash-checked and left unchanged.

The native frontend uses exact HF input token IDs, decodes exact output IDs with
the same tokenizer and reuses request validation and strict tool parsing. It
authenticates native model/runtime files, rejects silent context truncation and,
for unmerged LoRA, requires the native response to confirm the active adapter.

| Native profile | Frozen protocol | Coding | Tools | Native HumanEval |
|---|---|---:|---:|---|
| Q8 base | merged-v1 | 6/8 | 5/6 | Not run |
| Q8 merged lower-rate step18 | merged-v1 | 6/8 | 5/6 | Not run |
| Q8 plus FP32 lower-rate step18 | unmerged-v2 | 6/8 | 5/6 | Not run |
| Q8 plus FP32 higher-rate step72 | unmerged-v2 | 5/8 | 6/6 | Not run |

The merged pair showed no development gain and failed the tool floor. Keeping
the LoRA unmerged in FP32 did not fix those failures. The stronger full-rate
unmerged adapter recovered the tool scenario but regressed coding to 5/8. These
profiles failed prerequisites, so native HumanEval was not run. Their faster
small-fixture timings are not a basis for claiming equivalent quality. NF4 and
Q8 scores are distinct inference profiles, not interchangeable measurements.

## Grader and source validation

Generated Python runs in pinned
`python:3.12-slim@sha256:4840d514c583a4d3d8cad3940e68dee6f0f6f3635c12fcd0a3d74c21a5b93a54`.
The grader disables networking, mounts source read-only, drops capabilities,
runs as a non-root user and bounds CPU, memory, processes, file size and wall time.

A successful assertion sequence exits with a distinct completion status. Ordinary
`exit(0)`/`os._exit(0)` from generated code cannot pass by skipping tests. This
is a regression control, not an adversarial-grader guarantee. All 164 official
HumanEval reference solutions and all eight authored development references pass.
The escaped-comma fixture was checked at its actual parsed string value and was
correct; the failed generation retained a backslash contrary to the contract.

The original baseline HumanEval generations were rescored after completion-check
hardening. No generations or solved counts changed. Each measured HumanEval
profile attempted all 164 tasks once. Tests/reference answers were withheld from
generation; output-limit failures remain failures. HumanEval was used for
acceptance and selection, not an untouched final test set. Related material in
pretraining/public corpora cannot be excluded, and aggregate non-regression
would still permit individual case changes.

The final source passes **102 tests** in the complete environment. The minimal
CPU environment completes the same suite with two expected optional training-API
skips. The final patch is applied to a fresh checkout and checked against the
complete source manifest. Docker tests use the pinned image with CUDA hidden.
The repository includes a CPU GitHub Actions workflow; its remote run is tracked
separately from local validation.

The authorized cleanup deleted 12 inactive model/experiment directories and
recovered 90,592,219,136 bytes (90.6 GB / 84.4 GiB). Redundant dense BF16 and Q8
candidate outputs created by this task were later removed after preserving their
proof records, recovering another 13.83 GB. Original model inputs, adapters,
FP32 exports and the Q8 base remain on .54 for reproduction.

All seven protected Bonsai/Moss model/runtime directories were present at the
post-GPU check. Bonsai returned HTTP 200 with `status=ok` at
`2026-11-06T19:23:12.294632+00:00`; no task service remained active and the filesystem had
56.7 GB free. The coding endpoint was stopped.
An existing embedding gate can independently preempt Bonsai, so this is a
timestamped observation rather than a perpetual uptime claim.

The supervisor records Bonsai's prior state separately from a transient pause
marker and restores it through normal cleanup and `ExecStopPost`. A live probe
removed the marker and verified restoration from the durable record. Existing
model data, canonical memory state and global client/provider defaults were
preserved. No memory-store repair or alternative service was installed.

The real 0.8B p50c model was also reconstructed and verified on .54 using the
hardened provenance verifier. Both edited tensors and every unedited region
matched the expected reconstruction. This proves reconstruction integrity, not
a reproduced MATH-500 score or a new model-quality result.

## Findings and remaining work

1. Validation loss is insufficient for selecting a coding assistant. Retain
   functional and real-client gates, including broader regression checks.
2. Small tool fixtures establish a useful transport/format baseline but do not
   predict multi-module repair or recovery from repeated errors.
3. Runtime/quantization changes need fresh paired evidence. Artifact-preserving
   compilation alone cannot justify carrying NF4 scores over to Q8.
4. Probe the real client/managed-worker path. A direct backend call missed the
   Hermes profile boundary that selected a local terminal.
5. Preserve failed results, original evaluator sources and corrected-grader audits.
   A detector fix should not silently rewrite measured history.
6. Further training should use independently verified, task-disjoint repository
   repair and terminal-recovery data, a declared evaluation budget and a fresh
   held-out project set. No such future improvement is claimed here.

Other languages, larger repositories, unrestricted host-shell/MCP workflows,
long-context recall and multimodal coding remain unqualified. The completed work
provides a reproducible foundation and measured limits; it does not support the
original request's promise of perfect behavior.
