# Direct-edit paired acceptance boundary

No qualified 4B direct-weight candidate exists in the 8 November study. The
current `direct_edit54.py` broker accepts exposed practice only and rejects a
patch or final-evaluation role. It is not an independent quality evaluator.
This document specifies the gate for a later justified candidate; it does not
claim those acceptance stages ran or that their complete runner is implemented.

## Candidate admission

Before model-quality evaluation, require the exact official parent lock, a
reviewed reproducible failure, passing finite causal controls, a specific 4B
read/write mechanism and a non-fitting sparse BF16 derivation. Freeze the
candidate JSON, its before/after words and hashes, producer code, data exposure,
protocol, controls and source/runtime identities. An activation-transfer result
or a numeric patch validator cannot satisfy this scientific gate by itself.

Apply the frozen candidate only to a private verified language-model copy.
Recheck every changed and protected parameter. Preserve a separate unedited
parent; never open shared checkpoint/blob mappings writable. No full-checkpoint
copy, GPU window, quantization job or client VM is admitted without resource
capacity. Missing resources mean `NOT_RUN`; they do not authorize cleanup or
control of other jobs.

## Exposed paired development and regression

The surgeon may use predeclared development cases. Run original and edited BF16
weights under identical tokenizer/template, thinking mode, inference backend,
seed, budgets, grader and task order. Reset state/cache between cases and arms.
Record exact request/response attribution, output censoring, execution failures,
rescues and regressions. Compare executable outcomes; shorter output or a better
conditional operator score is not the primary quality metric.

Use the previously exposed fourteen coding/tool development cases, selected
Experimentos HE9 failures and OpenCode/Hermes fixtures as regressions. They are
not an untouched holdout. Preserve all failures and require no unexplained loss
on base-solved regressions. Do not replace this request with another all-164
HumanEval generation or relabel old adapter scores as direct-edit evidence.

## Independent final custody

A separate custodian holds untouched, family-disjoint cases and grader material.
The surgeon receives only the frozen interface, opaque task identities and the
final permitted aggregate result. Do not expose prompts, reference answers,
grader internals or intermediate final scores to candidate selection. A directory
owned by the same unrestricted agent is not an adversarial custody boundary.

Freeze the primary executable pass metric, task count, case-family definition,
paired seeds/order, handling of timeouts/censoring, minimum gain, regression
limits, uncertainty calculation and decision rule before the custodian runs
either arm. Report paired rescues/regressions and uncertainty with the full
denominator. A small development improvement cannot silently define the final
threshold. Incomplete, unattributed or identity-mismatched trials cannot become
passes. A failed final gate rejects the candidate; tuning on that same final
set requires a new research cycle and a new untouched confirmation set.

## Native OpenCode/Hermes and publication

BF16 success does not establish quantized behavior. Pin and authenticate original
and edited conversion/quantization sources and options, test both resulting
artifacts as another matched pair, and verify that the edit survives quantization.
Do not repurpose a trained-adapter export or merge route as a direct edit.

Actual client acceptance retains the user's native target: model-supported
262,144 context, Q8 K/V cache and 28,192 output allowance, with exact effective
sampler, template, backend, client versions and harness identities. Short CPU
diagnostics do not verify full-window recall or this deployment profile. Both
clients must use isolated, attributed file/project trials with independent
protected execution grading. Preserve failures, timeouts and source identities.
For the requested fresh-VM OpenCode replay, capture evidence that the client and
harness are absent before installing them in a newly admitted task-owned VM.
Preserve existing VM disks and separate evaluations; do not clear or repurpose
them to manufacture a fresh-harness claim. The same admitted VM/runtime and
frozen harness must serve both original and edited arms.

Promote or publish a successful direct model only after all frozen gates pass
and publication is authorized. A negative research report and source release
may still be useful; they must state `quality_evaluation: NOT_RUN` when no
candidate exists. Existing historical LoRA community weights keep their trained
identity and are never relabelled as a no-training direct repair.
